# E1 prospective real-service cohort specification v1

Status: **provider candidate selected; run freeze incomplete; no execution authorized or performed.** This is a separate real-observation cohort. The 19-case Decisions packet remains synthetic. E1 requires one genuine O→J→X→E sequence with externally inspectable settlement and service outcome, independent review, and reproducible receipt replay. An internally accepted E or a successful payment alone does not satisfy E1.

The repository now includes a local-only freeze preflight: `npm run prepare:e1-run -- docs/decisions-e1-run-freeze-template-v1.json`. It reads one JSON file, checks required evidence/approval references and fixed safety flags, prints missing gate names, and exits blocked. The command contains no HTTP, database, wallet, or payment client and cannot dispatch the provider request. Passing its reference checks would mean only “prepared for separate approval”; it cannot authorize or execute a run.

## Selected provider candidate and bounded task

Candidate: [Runway Weather Oracle](https://runwayoracle.com/), `GET https://runwayoracle.com/v1/oracle/v3/ord-edge` (Chicago O'Hare/KORD). Its first-party page and machine catalog describe x402 payment in USDC on Base (`eip155:8453`) and list a $0.05 live-telemetry / $0.01 degraded-fallback price. Those pages identify a real, suitable service and a supported payment network; they do **not** establish that this provider is operationally reachable now, disclose a response schema, or document a signed result, stable request ID, or independently retrievable request log. The candidate is therefore **not yet qualified for execution**. No API endpoint or NWS observation endpoint was called in this task.

Proposed single-call task: request one KORD current-temperature nowcast and evaluate it against an independently captured official NWS KORD observation. Proposed success boundary, to freeze before any request: response is provider-schema-valid JSON; identifies KORD and the source observation time; contains a finite temperature in a stated unit; the matching NWS observation is no more than five minutes from that source time; absolute temperature difference is at most 2°F after explicit unit conversion. The source overlap is disclosed: Runway says its estimates use the same NWS station family. This test checks delivery and a bounded observed-value criterion, not independent forecast skill. An independent reviewer must decide whether the source overlap is sufficient for E1's observation/outcome provenance; if not, choose a different task/provider before execution.

For outcome evidence, the planned reference is the official [NWS API](https://www.weather.gov/documentation/services-web-api), station `KORD`, with observation payload, timestamp, response headers, and SHA-256 retained. The NWS API is public and intended as open data; its documentation requires clients to respect reasonable rate limits. Provider evidence must include the exact original request/response, status, response headers, payment response, and a provider-originated request identifier or retrievable provider-side record. A client-generated hash and the Base transfer alone are not provider-side delivery proof. The run remains blocked until the exact response schema and acceptable provider-side evidence are confirmed and frozen.

## Pre-execution freeze record

Before any call, the operator and an independent reviewer must sign a new immutable run record containing: cohort ID/version and this specification's Git commit/hash; isolated staging deployment and schema; deterministic policy and code commit; operator and reviewer identities; exact task and expected deliverable; provider legal name, HTTPS endpoint, account and eligibility; provider request template and canonical hash method; allowed route and `base_usdc_external.v1` proof profile; observation source and freshness bound; evaluation rubric with pass/fail criteria and deadline; permitted outcome artifacts; issuer public trust registry; approved payer/recipient addresses; judgment fee, service price, gas ceiling, per-call and aggregate limits; approval identity and expiry; stop conditions; and Decisions feature-flag state. A changed item requires a new run version and fresh approval. This document alone is not that run record.

Proposed hard ceilings for review: one provider payment of at most **0.05 USDC on Base** (require the live-telemetry quote; stop if the provider quotes differently), one paid Judgment of at most **0.25 USD equivalent on the configured judgment rail**, combined transaction/facilitator fees on both networks at most **0.25 USD equivalent**, and total outlay at most **0.55 USD equivalent**. These are ceilings for a future signed run record, not an authorization. The current code's new paid Judgments require the `eip155:4663` USDG rail when payment is enabled; the candidate provider uses Base USDC. They are two distinct settlement paths. Freeze the actual Judgment challenge, USDG recipient, both fee estimates, and conversion source before approval. If either chain cannot fit the caps or a segregated staging signer is unavailable, stop. Use a segregated wallet and test issuer unrelated to production keys. No provider request, transaction, or payment has been performed.

## Cohort and causal sequence

| Case | Frozen expectation | Permitted receipt pattern | Evidence requirement |
| --- | --- | --- | --- |
| Positive real-service task | Fresh, reviewed, scoped facts support a small authorized task. | Genuine O, paid signed J, one externally executed X, then independently reviewed E in isolated staging. | Provider catalog/source capture; quote and payment proof; original signed X submission; finalized transfer; provider request ID and delivered result; rubric and independent outcome review. |
| Denied action | Known provider, policy, or budget veto. | O and, only if a separately approved assessment fee is paid, a `do_not_spend` J. No X or E. | Authentic negative facts and deterministic denial. A quote is not a paid J. |
| Insufficient evidence | Missing, stale, mismatched, or unverified observation. | Free `insufficient_evidence` response; O only if a genuine observation exists. No billable J, X, or E. | Missing/stale reason and zero-charge trace; no synthetic O to complete a chain. |

1. **Observation.** After approved staging and run freeze, capture the official NWS source artifact and retrieval time before assessment. A qualified reviewer records provider identity, task/intent binding, route, constraints, exact provider schema and quote, confidence basis, freshness expiry, and content digest. A catalog flag of `live` by itself is insufficient. The pre-spend model-visible packet contains only information available now; outcome data are withheld.
2. **Judgment.** Run the existing deterministic pre-spend policy in isolated staging with Decisions disabled for authorization. Record full normalized input, policy/config commit, evidence set, decision clock, returned decision and reason, quote, and signed J only if its separate RH/USDG fee and settlement are authorized. Independently replay the result from frozen inputs. No model suggestion can change evidence, budget, or ALLOW. Insufficient evidence remains free and does not create a billable J.
3. **Execution.** Only after separate approval for the Judgment settlement, provider request, and external payment, obtain the separately required execution capability and perform exactly one frozen request using the approved external payer. Keep original signed proof input; verify Base finalized USDC Transfer, exact payer/recipient/amount, request hash, judgment window, and uniqueness. The provider must return an independently inspectable request ID and response artifact; a transfer is not evidence of delivery. If execution is denied, timed out, over budget, or ambiguous, stop and classify pending/invalid rather than fabricating X.
4. **Evaluation.** A reviewer who did not issue J or execute the task compares the actual provider response to the frozen rubric, records inspected artifact hashes, identity, time, reasons, and disagreement if applicable. Only after this review may a staging E be submitted and treated as a candidate verified outcome. The current Evaluation service accepts internal provenance and nonempty refs without checking external truth; therefore its acceptance is **not** the independent verification. Its score effect must remain confined to isolated staging; no benchmark step writes a production E or reputation projection.
5. **Replay and publication.** Re-read O, J, X, E after process restart from the isolated durable store. Verify strict schemas, hashes, signed J against pinned public keys, exact parent pointers, subject/intent, state/time order, X proof body and finalized settlement, E evidence and reviewer authority. Reproduce deterministic J from the frozen pre-spend input and code/config; record any inability to reproduce. Freeze a redacted evidence manifest with artifact hashes, source coverage, reviewer records and explicit exclusions. Have a second independent reviewer sign the E1 conclusion.

## Stop rules and acceptance

Stop before any external transaction if provider identity, response inspectability, quote, route, wallet isolation, evidence freshness, capability, approvals, or caps fail. Stop after a transaction if settlement or outcome cannot be independently verified; preserve the ambiguous evidence and do not mark E1 complete. No retries that might double-spend without reconciling settlement and idempotency first. No production writes, billing activation, live Decisions spend influence, or IPX economics changes. A denied case is a safety observation, not an executed outcome. One verified loop demonstrates the mechanism for E1; it cannot estimate a false-ALLOW rate or satisfy E2/E3.
