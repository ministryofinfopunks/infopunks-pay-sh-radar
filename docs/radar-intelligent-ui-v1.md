# Radar Intelligent UI v1: read-only decision presentation

Status: **integration candidate**. This patch is not a deployed release, not a completed causal-loop audit, and not spending authorization. Canonical authority remains with the existing Observe -> Judge -> Execute -> Evaluate services.

## Scope

- `GET /v1/decision-views/:id` resolves a stored canonical JudgmentReceipt into a minimal redacted, Zod-validated presentation contract. This request never runs a model, takes a payment, writes a receipt, or requests an authorization.
- `/radar/intelligent-ui` lets an operator enter an existing canonical judgment ID.
- `/radar/decisions/:id` renders the canonical state, assessed fee (not target spend), recorded reasons, verification status, observation ancestry, and an inspectable machine contract.
- Execution authorization is intentionally always `false` in the projection. No action generated by the interface can obtain or exercise a capability. The execution gate stays independent.
- Existing diagnostic preflight cards are not converted into canonical spending judgments and retain their existing semantics.
- The exact evaluation-history knowledge boundary is **not present** in canonical receipt v1; the projection must show `not_available_in_canonical_v1` rather than inventing a score dependency.
- For canonical receipt v2, the projection exposes the committed evaluation-reference hash only when the context replay and trusted issuer verification both pass. If the context is absent, invalid, or the judgment is untrusted, it reports `unavailable` and the assessment is ineligible.
- `GET /v1/decision-views/:id` is documented in `/openapi.json`, sends `Cache-Control: no-store`, and is limited to 60 requests per minute per client IP.

## Data and safety boundaries

1. Issuer verification uses the trusted, separately configured `JudgmentIssuerTrust` rather than a key supplied in the receipt.
2. Full receipt ancestry is checked using the existing `verifyReceiptChain`; an unsigned, invalid, expired, or not-yet-valid record never becomes an eligible assessment.
3. The view includes no raw observation payload, provenance object, private keys, execution capability, wallet signing action or settlement secrets.
4. Inspect and copy are the only allowed actions. Browser control state does not call a judgment endpoint.
5. The assessment fee from a judgment is never presented as a service price or execution amount. Provider/route/chain are not invented when unavailable from the canonical record.
6. Public endpoint exposure matches the existing public receipt read model. The view endpoint applies a per-IP rate limit; before production deployment, review enumeration, ID privacy, proxy/IP configuration and tenant-specific access. If future receipts contain privileged information, move this view behind authenticated authorization rather than expanding the public schema.
7. The UI is data-derived, not model-authored. Model-selected composition must be separately threat-modeled, read-only and constrained by a catalog before use.
8. Client UI can be tampered with. It has no capability to create or authorize execution and must never be treated as a security boundary.

## Optional OpenUI assessment

OpenUI (`thesysdev/openui`, MIT) currently offers `@openuidev/lang-core` and `@openuidev/react-lang` with constrained component libraries, parsing, and streaming React rendering. Its renderer can also expose tool execution through `toolProvider` and action handlers; do **not** supply write tools or an unreviewed MCP connection to a model-generated Radar view. For the first pilot, create read-only wrappers around `decision_verdict`, `evidence_inspector`, and `receipt_identity`, with IDs bound to the verified DecisionView projection. Never give model output raw receipt JSON to overwrite bound facts.

Evaluation steps, on a separate dependency sandbox branch:

1. Pin specific OpenUI versions and inspect Node/React/Zod peer ranges, SBOM, license and dependency advisories.
2. Build a component-only, read-only library with no `Query`, `Mutation`, `toolProvider`, write actions, or evaluation-time network authority.
3. Render fixtures: verified proceed, limited test, veto, insufficient evidence, invalid signer, expired record, absent causal history, corrupted renderer input.
4. Compare accessibility, load time, parser/re-render overhead, CSP policy and JS bundle size with the deterministic React implementation.
5. Reject the pilot if unknown components, unsafe actions, incorrect binding, arithmetic from model text, or stale state can appear authoritative.
6. Only then explore safe, bounded server-side model composition. The signed receipt projection, never an LLM response, remains the source of truth.
