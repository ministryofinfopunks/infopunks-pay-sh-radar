# PR #35 release and recovery note

This note records the release boundary for monitor delta persistence. It does not authorize a production configuration change, migration, deployment, or monitor run.

## Effective monitor behavior

`INGESTION_ENABLED=false` and `RH_CHAIN_AUTOMATION_ENABLED=false` do not disable the monitor. In the production service configuration, `MONITOR_ENABLED`, `MONITOR_MODE`, and `MONITOR_INTERVAL_MS` are configured (the runtime-config log intentionally redacts their values). Repeated `monitor_job_failed` entries on 2026-11-04 and 2026-11-05 are spaced about 900 seconds apart, demonstrating an active 15-minute scheduler. The latest durable monitor row is a successful `safe_metadata` run finished at 2026-07-18 11:22:43 UTC; later scheduled attempts failed persistence.

Source defaults are `MONITOR_ENABLED=false`, `MONITOR_MODE=disabled`, and `MONITOR_INTERVAL_MS=900000` when the interval is absent. The last persisted mode was `safe_metadata`; the exact live mode setting is not exposed in the redacted configuration record.

After deployment and application readiness, the configured scheduler can call `runMonitor` at its next interval tick and commit a delta. There is no monitor invocation in startup itself. The admin-only `POST /v1/monitor/run` route can cause a delta immediately. Neither ingestion nor RH automation switches gate either path. The write transaction records monitor events/run/state changes and the current full-snapshot checkpoint ID; it does not insert an `intelligence_snapshots` row.

## Ordering and restart qualification

The transaction advisory lock serializes full-snapshot and delta transactions. Qualification found that advancing a checkpoint while retagging only the last folded run dropped earlier folded deltas from the next replay window when the caller held a stale in-memory snapshot. The writer now retags every folded monitor run to the new checkpoint. This preserves the replay chain across repeated checkpoint folds.

The PostgreSQL 18.6 integration test now covers a stale full snapshot overlapping a newer delta, two successive checkpoints, several deltas in one checkpoint, restart restoration, and exactly-once event/run/evidence assertions. Another integration case executes the previous loader's actual query/result contract. Before a full checkpoint includes a delta, that loader reads only `intelligence_snapshots.snapshot` and does not read the corresponding `monitor_runs.state_delta` or linked events. The rows remain in PostgreSQL, but the previous application does not expose them in its in-memory state.

Assessment freshness is calculated at the recorded monitor completion time. The monitor does not change the provider's catalog `lastSeenAt`; a Jan 1 observation assessed by a Jan 10 run remains nine days old and scores freshness 28 under the current formula. On restart, replay uses the persisted run completion time rather than the restart clock, so an old run does not acquire a newer assessment timestamp.

## Startup DDL and ordered maintenance release

Read-only production catalog inspection on 2026-11-05 found the new columns and indexes absent. `infopunks_events` had about 70,235 estimated rows, a 1.26 GB heap, 59 MB of indexes, and 1.76 GB total relation size. `monitor_runs` had about 2,467 estimated rows and 110 MB total size. The historical snapshot table was about 11 GB total; PR #35 does not alter or index it.

The startup schema batch creates missing tables, conditionally adds `infopunks_events.monitor_run_id` and `monitor_event_order`, and adds `monitor_runs.snapshot_id`, `state_delta`, plus conditional compatibility columns `mode`, `reachable_count`, `degraded_count`, and `skipped_reasons`. It ensures the existing entity index and creates ordinary indexes `infopunks_events_monitor_run_idx` and `monitor_runs_snapshot_started_idx`.

Pre-applying every column and index does not remove the need to bound startup checks: `ensureSchema()` still executes `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` on startup and repository operations, which may still take relation locks while checking existing objects. PR #35 now wraps the complete schema batch in one transaction with `SET LOCAL lock_timeout='30s'`, `statement_timeout='5min'`, and PostgreSQL 18's `transaction_timeout='15min'`. Failure rolls back the batch and is surfaced to startup/readiness. The settings end at transaction completion; no global `PGOPTIONS` or role/database timeout change is needed.

The indexes remain ordinary, non-concurrent builds. They scan the event table and block writes to their target tables while building. That is acceptable only inside an enforced write-free maintenance window of at most 15 minutes. Each statement is capped at five minutes, lock waits at 30 seconds, and the whole DDL transaction at 15 minutes. On any timeout or DDL error, the transaction rolls back; do not switch to concurrent indexes without separate testing.

### Required order

1. **Quiesce.** Record exact prior `MONITOR_ENABLED`, `MONITOR_MODE`, and `PAYSH_BOOTSTRAP_ENABLED` values. Put the service in its existing maintenance mode to block HTTP/manual admission. Temporarily set `MONITOR_ENABLED=false`, `MONITOR_MODE=disabled`, and `PAYSH_BOOTSTRAP_ENABLED=false`, then explicitly deploy/restart the current live SHA so the running process receives them. Saving values alone does not change an existing process. Require the old instance to report shutdown completion and Render to show it deactivated. `StoreJobCoordinator.close()` rejects later jobs, drops queued timer follow-ups, and awaits active work; timer close hooks clear intervals. Verify no active application transaction or ungranted lock remains in `pg_stat_activity`/`pg_locks`; do not cancel a backend. Require an accepted persisted snapshot before proceeding because the bootstrap suppression assumes load/restore can succeed without fetching or writing a catalog.
2. **Bounded DDL.** Keep maintenance mode on and freeze all operator/admin calls. The scheduled ingestion switch is already false; RH automation is false. With monitor and startup bootstrap disabled and every old instance drained, run the exact additive schema batch in one transaction with the same local lock, statement, and transaction limits. Verify all columns/index definitions, unchanged latest snapshot ID, no waiting locks, and successful commit. Abort on a 30-second lock timeout, five-minute statement timeout, 15-minute transaction timeout, database degradation, or unexpected writer.
3. **Guarded merge/deploy with writers disabled.** Recheck main `c8d199354ee2cf21af1d3891d49e533f359e5001` and the final PR head. Merge only with an exact-head guard; require merge parents to be those two SHAs and merge tree to equal the PR head tree. Deploy only that merge SHA with auto-deploy off. Keep monitor disabled, bootstrap disabled, Solana ingestion false, and RH automation false. Startup repeats the schema batch under transaction-scoped timeouts; the already-created indexes should be no-ops. Keep maintenance mode on until startup load and database readiness pass.
4. **Bootstrap acceptance.** Restore the prior `PAYSH_BOOTSTRAP_ENABLED` value and explicitly restart/deploy the same merge SHA while monitor scheduling remains disabled. A rejected stale/invalid catalog should write only the bounded ingestion diagnostic; a valid accepted catalog may perform its normal snapshot write, which must be recorded. Stop on database/persistence errors, unexpected snapshot writes, or failed readiness. Then leave maintenance mode only after the app and safe reads pass.
5. **Monitor restore.** Restore the recorded monitor settings (including the exact prior `MONITOR_MODE`, not just the boolean) and explicitly deploy/restart the same merge SHA. Keep Solana ingestion and RH automation false. No admin/manual monitor runs are allowed. A successful scheduled delta may begin at the first configured timer tick after the new process starts.
6. **Two natural runs and restart check.** Allow two full configured monitor intervals—about 30 minutes at the observed 15-minute cadence—plus job completion and restart verification. For each run, verify run/event/state rows, the checkpoint link, no duplicate evidence, no `intelligence_snapshots` insert from the monitor, and no persistence error. Then stop the single instance cleanly and start the same deployed SHA; verify restart replay restores both runs/evidence exactly once and API state agrees before declaring acceptance. This observation period is separate from the 15-minute DDL cap.

The enforced write barrier is the combination of Render maintenance mode, effective disabled monitor/bootstrap settings delivered by a real restart, the already-false scheduled ingestion/RH settings, and confirmed process/transaction drain. Manual endpoints remain callable in application code, so maintenance mode and an explicit operator freeze are required throughout DDL; feature switches alone do not block manual jobs.

## Recovery boundary

The previous application reads only the latest full snapshot. After deltas commit, it ignores uncheckpointed monitor rows and would hide those updates from visitors. Do not roll back to that code, delete delta rows, retarget them with ad hoc SQL, or force a large snapshot checkpoint.

The previously qualified delta-capable parent `7013a5912da98c407cdae9666b5e128e6c623472` is a possible fallback only for a failure isolated to the new schema-timeout wrapper, after the schema batch has committed and while all writes remain disabled. It is not a general remedy for a delta read/write defect.

If the candidate fails after deltas commit: immediately enter maintenance mode; set both monitor settings to disabled and deploy/restart the selected recovery code so the process actually stops scheduling; wait for process exit and transaction drain; preserve the database unchanged; and capture a bounded logical backup of the latest checkpoint's non-null `state_delta` runs and linked events. If the failure is not proven to be confined to the timeout wrapper, remain in the safe stopped state with visitor writes blocked until a corrected delta-capable artifact passes restart/replay qualification. Do not serve the previous snapshot as though it includes the missing monitor results. Keep auto-deploy off and leave Solana ingestion and RH automation false.

Do not describe this release as a PostgreSQL SIGKILL fix.

## Startup DDL and bounded deployment stop plan

Read-only production catalog inspection on 2026-11-05 found the new columns and indexes absent. `infopunks_events` has about 70,235 estimated rows, a 1.26 GB heap, 59 MB of indexes, and 1.76 GB total relation size. `monitor_runs` has about 2,467 estimated rows and 110 MB total size. The queried historical snapshot table is about 11 GB total; PR #35 does not alter or index it.

At startup, `ensureSchema()` adds nullable columns without defaults, then runs ordinary (non-concurrent) `CREATE INDEX IF NOT EXISTS` statements. The nullable column additions are metadata-only on supported PostgreSQL versions but require brief `ACCESS EXCLUSIVE` locks and can wait behind existing transactions. The event index needs a table scan over the large event heap; ordinary index creation permits reads but blocks writes to that table for its duration. The run index has the same locking pattern on the smaller run table. Startup executes this schema bootstrap before the application finishes loading persisted state, so a lock wait or index build can delay readiness and contend with the still-running old instance.

Before any separately authorized deployment, record database connectivity/circuit health, active transactions and locks, relation sizes, free disk, current snapshot ID, and the existing readiness/startup baseline. Because the independent monitor is currently active, do not attempt the rollout while it is writing. A separate authorization is required to disable and drain that scheduler before startup DDL. Keep ingestion and RH switches false and auto-deploy off.

During an approved rollout, stop if the new instance is not ready within five minutes, an existing instance loses readiness, a DDL lock wait exceeds 30 seconds, the database circuit degrades, or any unexpected snapshot write occurs. Preserve the blocker PID/query and deployment logs. Do not repeatedly redeploy or kill a backend. Keep the last healthy instance serving only if Render has not terminated it; otherwise stop the operation and use the record-preserving recovery procedure above. Do not describe this as a PostgreSQL SIGKILL fix.
