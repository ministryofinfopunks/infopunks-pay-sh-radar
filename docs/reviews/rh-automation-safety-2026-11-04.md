# RH automation safety qualification

This correction depends on PR #32 and must run only after the older collectors have stopped. Its locks do not expire or renew: renewal is not fencing, and RH jobs write through services that do not accept fencing tokens. Each run uses a unique lock owner. Existing rows, including expired legacy leases, block acquisition. The configured TTL remains accepted for compatibility but does not govern these locks. A crash, ambiguous acquisition, or failed release can leave a job blocked. After positively confirming that every process that could own the row has stopped, an operator can inspect and remove the specific orphan row; never delete a row merely because its old timestamp has expired. Lock deletion, database restore/rollback or other external loss of the row while its owner runs is outside this guarantee: do not perform these operations while jobs may be active. Lost durable database state cannot be fenced by this change. There is no renewal to fail and no automatic reacquisition on expiry or ownership loss.

On shutdown the application clears RH timers, rejects new RH work, waits for tracked work (including lock release and run persistence), then closes dependent stores and the database. A hung job delays graceful shutdown. A forced kill can leave a lock requiring the recovery above. This change does not address PostgreSQL SIGKILLs.

The test `rh-automation-safety.test.ts` reproduced both baseline risks on PR #32 before the correction: a second coordinator ran after the TTL and an application store closed before an active scheduled write. The PostgreSQL case also reproduced stealing an expired legacy row. The disposable PostgreSQL tests require `RH_SAFETY_TEST_DATABASE_URL` pointing only to a disposable database.

Activation review: the previously supplied configuration remains authoritative. Only the effective `RH_CHAIN_RECEIPT_DRAFT_CRON` (unset or exact cron expression), `RH_CHAIN_MARKET_INGESTION_ENABLED`, and `RH_CHAIN_MARKET_HISTORY_ENABLED` need confirmation where they affect activation. Startup defaults provisionally indicate no receipt cron and both market flags false; this is not proof of deployed effective values. Automation itself also enables market capture and history in the application, regardless of those two flags. Confirm intended behavior against the effective settings before activation.
