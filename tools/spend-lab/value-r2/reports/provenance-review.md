# Production provenance review — release review blocker

**HOLD. Production population and deployed revision UNKNOWN. No production database, wallet, staging service or external provider was accessed. No core policy or release gate is changed.** This is a static/code-path audit of PR #16 at `9712fa304751565fac998460eca030d6247d4a1e`, with executable characterization vectors in `provenance-audit.ts` and the R2 tests.

`src/security/evidenceProvenance.ts:45` currently accepts `{catalog_source: 'live'}` with absent `fixture`, `simulation`, `evidence_class`, `spending_authority` and `external_economic_activity`. The environment test only excludes the exact local-lab name; absent or other environment strings also pass. Explicit null/malformed authority values generally fail, but omission is accepted. Therefore absence of an authority declaration does not currently force abstention. A source label alone is not independently verified evidence.

Affected consumers:

- `src/services/judge.ts` filters economic observations through this predicate. Candidate/policy hashes, fresh evidence and subsequent authorization checks remain required, but absent provenance declarations are not a veto here.
- `src/services/decisionContextService.ts:24` uses the same predicate in both paid issuance and frozen V2 context replay. Its full integrity/scope/freshness/fact checks do not independently establish that an omitted authority field was reviewed. The R2 characterization test reproduces a 402/proceed quote using the existing legacy-only fixture; it does not settle a payment.
- `src/services/receiptAuthorityService.ts:31` validates historical receipt integrity/ancestry; V2 replays the frozen decision context. V1 receipts can remain historically valid without a current explicit live-authority classification. The simulation-specific domain guard is valuable but is not a general retrospective authority classifier for every legacy record. A valid signed historical chain is not blanket permission for new execution.
- The SDK, execution gate and provider boundary still require signed judgments, separately issued execution capabilities, exact bindings, expiry and replay controls. Provenance declarations neither replace these controls nor prove settlement/outcome. No absent field should be “repaired” by inventing an execution capability or completed receipt chain.

`explicitReviewedProvenance` is a stricter **diagnostic in tools only**. Even when every declaration is present, it proves only the presence of labels. It is deliberately not installed as production policy and is not presented as sufficient external authority. The machine-readable audit shows every vector and every acceptance difference. No count of actual affected production records is inferred from synthetic vectors or repository fixtures.

Required independent remediation review before a live pilot:

1. Inventory actual deployed source/schema/ingestion adapters and immutable observations with read authority separately granted to an independent data custodian. Record missing/ambiguous fields without changing historical records. Distinguish absent, null, false, unknown and positively verified authority.
2. Define a versioned reviewed intake contract: source/collector identity, authenticated provenance/attestation, environment, observed and ingested time, freshness, exact subject/candidate/intent/policy binding, permissible evidence use and independent reviewer. “Live,” “verified” or a hash alone is insufficient. Resolve network/rail-specific settlement finality and outcome proof separately.
3. Quarantine legacy/ambiguous provenance from **new** spending decisions until independently reobserved or reattested. Preserve the old receipt/hash/history and link a new observation; do not backfill assumed authority, rewrite hashes, delete records or reinterpret historic payment as permission.
4. Propose any strict default-deny reader/adapter/migration in a separately reviewed implementation with legacy replay compatibility tests, tenant isolation, canonical context replay, authorization/recovery tests and exact-source requalification. Economic gains cannot justify weakening fresh/sufficient evidence or silently admitting legacy omissions.
5. Security, provenance/data, database/migration and independent evaluation reviewers must sign the exact source/contract/actual data scope. Names, approvals, dates and deployed population remain unassigned/unknown. Existing release gates remain HOLD regardless of the economic report.
